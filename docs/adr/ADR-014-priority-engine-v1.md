# ADR-014: Priority Engine v1 — Factors, Formula, Weights

## Status
Accepted — weight values ratified by the product owner (M2 sign-off, reaffirmed 2026-09-08)

## Date
2026-09-07

## Context
Blueprint §22 specifies a **deterministic** priority engine with a weighted-sum
"Initial formula" over eight normalized (0–1) factors. PRD §6 frames priority
conceptually (`Career Relevance × Skill Gap × … × Available Time`) and requires
the result be **"explainable to the user"**. PRD §2.7 — "the score is an
indicator, not the objective". Blueprint §33 lists **"initial scoring weights"**
as an open decision to be made through an ADR rather than buried in code.

Milestone 2 introduces Objectives, Milestones, Tasks and Daily Planning. Most of
the eight §22 factors depend on domains that do not exist yet (Career, Skills,
Projects — Milestone 3+). Only two have real signal in M2 (`urgency`,
`availableTimeFit`), plus two that can be approximated.

## Decision

### 1. Formula — adopt Blueprint §22 exactly
`priority = Σ (weightᵢ × factorᵢ)`, factors clamped to `[0, 1]`, weights summing
to 1, so `priority ∈ [0, 1]`. The shipping weights are Blueprint §22's:

| Factor | Weight | M2 status |
|--------|-------:|-----------|
| `careerRelevance` | **0.20** | **proxy** — normalized objective priority (see §3) |
| `skillGap` | **0.20** | neutral `0.5` (no Skills domain until M3) |
| `dependencyImpact` | **0.15** | neutral `0.5` (no dependency graph until M3) |
| `projectImpact` | **0.15** | neutral `0.5` (no Projects domain until M3) |
| `interviewValue` | **0.10** | neutral `0.5` (no Career/interview data until M3) |
| `urgency` | **0.10** | **computed** from `due_at` / objective `target_date` |
| `availableTimeFit` | **0.05** | **computed** from `estimated_minutes` vs profile `available_daily_minutes` |
| `historicalCompletionProbability` | **0.05** | **computed** — user's completed-task ratio, `0.5` with no history |

### 2. Configurable, not hardcoded
Weights live in `application.yml` under `orbit.priority.weights.*` and bind to a
`@ConfigurationProperties` record. Startup validates they sum to `1.0 ± 0.001`
and rejects the context otherwise. A `weightsFingerprint` (short hash of the
ordered weights) is stored in every `priority_reason` so a score can always be
traced to the weight set that produced it.

### 3. M2 factor providers (pure functions, deterministic)
`PriorityEngine.score(input, referenceInstant)` is a pure function — same inputs
always yield the same score and the same explanation. `referenceInstant` is an
explicit parameter (not `Instant.now()` inside the engine) so `urgency` is
reproducible in tests.

- **`urgency`** — from the effective deadline (`task.due_at`, else the parent
  objective's `target_date` at end-of-day, dampened ×0.8 because it is less
  specific). Days-until → score: `≤0 → 1.0`, `≤1 → 0.9`, `≤3 → 0.75`,
  `≤7 → 0.55`, `≤14 → 0.4`, `≤30 → 0.25`, else `0.15`. No deadline at all → `0.3`.
- **`availableTimeFit`** — `estimated_minutes` vs `available_daily_minutes`
  (profile; default 120 when unset): fits in half the budget → `1.0`; fits in
  the budget → linear `1.0 → 0.6`; over budget → `max(0.15, budget/estimate)`.
  No estimate → `0.5`.
- **`historicalCompletionProbability`** — `completed / (completed + skipped)` over
  the user's non-deleted tasks; `< 5` resolved tasks → `0.5`.
- **`careerRelevance` (proxy)** — the parent objective's manual `priority`
  (`1..5`) linearly mapped to `[0.2, 1.0]`. This is an explicit **M2
  approximation**: "the user said this objective matters" is a legitimate
  career-relevance signal in the absence of a career target. Replaced by the
  real Career Engine computation in M3 with **no formula or weight change** —
  only the provider swaps.
- The four neutral factors return a constant `0.5` and are marked
  `source: "neutral-default"` in the explanation.

### 4. Explanation (`priority_reason` JSONB, Blueprint §10)
```json
{
  "score": 0.58,
  "engineVersion": "v1",
  "weightsFingerprint": "a1b2c3d4",
  "computedAt": "2026-09-07T09:00:00Z",
  "factors": {
    "urgency":          { "value": 0.75, "weight": 0.10, "contribution": 0.075, "source": "computed", "detail": "due in 2 days" },
    "availableTimeFit":  { "value": 1.0,  "weight": 0.05, "contribution": 0.05,  "source": "computed", "detail": "45 min fits a 120 min budget" },
    "careerRelevance":   { "value": 0.8,  "weight": 0.20, "contribution": 0.16,  "source": "proxy",    "detail": "objective priority 4/5" },
    "skillGap":          { "value": 0.5,  "weight": 0.20, "contribution": 0.10,  "source": "neutral-default", "detail": "Skills domain not yet available" }
  }
}
```
The UI renders this directly as the "Why this?" rationale (UX §16, §17). No text
is generated by an LLM.

### 5. When scores are computed
On task create and on every task update that changes `estimated_minutes`,
`due_at`, or `status`, and for every task pulled into a daily-plan generation.
`priority_score` + `priority_reason` are persisted on the task row. A recompute
of one user's tasks is O(tasks) and runs inline.

## Alternatives Considered
1. **PRD §6's multiplicative model** (`f1 × f2 × … × f7`) — rejected for M2: a
   single low factor (e.g. every neutral `0.5`) collapses the whole score toward
   zero, which is meaningless while six of eight factors are placeholders.
   Blueprint §22's additive model degrades gracefully. Revisit if §22 is revised.
2. **M2-only subset formula** (just `urgency` + `availableTimeFit`, re-weighted) —
   rejected: it would have to be re-derived and re-tested when each domain lands,
   and diverges from the authoritative §22 formula. The neutral-default approach
   keeps one formula for the product's life.
3. **Hardcoded weights** — rejected by Blueprint §33 (must be an ADR-tracked,
   surfaced decision) and the Milestone 2 brief.

## Consequences
- **Positive:** one formula from M2 onward; every score fully explainable and
  reproducible; weights are one config change away from tuning; adding a real
  factor provider in M3 needs no formula/schema change.
- **Negative:** M2 scores are dominated by `careerRelevance` (the proxy, 0.20) and
  the neutral mass (0.60 of the weight is constant `0.5`), so in M2 the engine
  mostly ranks by *objective priority then urgency then time-fit*. That is a
  reasonable M2 behaviour but it is not yet "smart". Documented so it is not
  mistaken for the finished engine.
- **Negative:** `urgency` makes a task's score time-dependent (it rises as the
  deadline nears). This is intended; "deterministic" (§22) means no randomness /
  no opaque model, not time-invariant.

## Decision needed (product owner)
Confirm or adjust, before or after M2 ships:
1. **The eight weights** — shipping as Blueprint §22's values
   (`0.20 / 0.20 / 0.15 / 0.15 / 0.10 / 0.10 / 0.05 / 0.05`). These are the
   spec's own numbers; sign-off is ratification per Blueprint §33.
2. **The `careerRelevance` ← objective-priority proxy** for M2 (§3).
3. **The `urgency` day thresholds** and **`availableTimeFit` curve** (§3) — these
   are not in any spec; they are this ADR's proposal.
